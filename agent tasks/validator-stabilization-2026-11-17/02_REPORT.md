### Count accounting: do not conflate the denominators

1. **Windows Security log records existing in the time range**: not measured here. The query is scoped by XPath and may be affected by journal loss, permissions and policy state.
2. **XPath results returned by `EvtNext`**: bounded to 2048 and normally to the deadline, but not reported.
3. **XML results rendered and passed to `_record`**: not separately counted. `EvtRender` failure marks a failure without giving a rendered total.
4. **Records matching the process path and relevant rights mask**: only eligible, in-range, unique records increment group counters; total relevant *event records* is recoverable from a complete **local** report as `len(confirmed.rows)+confirmed.rowsOmitted+len(ambiguous.rows)+ambiguous.rowsOmitted`. That is **not** the total the Windows query examined and may itself be a lower bound if the query failed/was truncated.
5. **Counts per right**: `readRecords` and `writeRecords` count records bearing 0x10 and 0x20 respectively, not byte transfers, instructions, memory changes, or repeated API calls. A single record with mask 0x30 increments both. Windows may coalesce repeated right exercises on a handle (functional_updates.md:127-131).
6. **Confirmed / ambiguous**: mutually exclusive attribution of a processed record, not two independently verified sets of actor identities. A local `confirmed` record means use by the Validator's *own pinned reader*, not proof of a foreign cheat.
7. **Omitted correlation records**: not equivalent to raw journal events missed by Windows. There are two successive small sample/group limits (24 local rows per group; 12 grouped correlation rows).

## 5. Own-reader attribution, identical paths, and cross-sensor evidence

- AuditSession (security_audit.py:161-175) holds identity for the target reader handle and uses `owner=(os.getpid(), int(handle))`. Those IDs are sufficient for exact *own pinned reader* attribution **only when the timestamp is within a trusted span**. They are not sufficient to prove a foreign handle lifetime.
- With `spans=[]` (as in the clock-degraded path), the own reader's events are assigned `attribution=run_boundary_unknown` and can consume all 24 ambiguous detail slots. This is **possible and mechanically demonstrated by source**, not a measurement of who authored the 24 entries in this capture. Without source PID/handle and EventRecordID data, own-reader saturation is an unverified hypothesis.
- `ObjectName` matching uses normalized game image paths, not PID+creation target identity (security_audit.py:123-124, 167). Two live target processes with the same path can produce indistinguishable 4663 target names. Do **not** reclassify such events as exact solely via EXE path.
- Existing Windows owned-process stand (scripts/security_audit_acceptance.py:108-149, documented in functional_updates.md:160-171) previously observed 2 reads + 2 writes collapsing to one record per right on one target, one additional read on another same-image target, and numeric handle reuse. It correctly left foreign events ambiguous and verified restoration in that historical stand. The exact past stand source revision was not independently recovered; **do not claim it passed on current HEAD**.
- SourceLifetimes (rights_correlation.py:49-122) retains at most 24 identity-checked process handles and attempts at most 128 source identities per run. `get_times` bounds source PID/creation/exit and helps reject PID reuse (lines 90-113), but cannot prove continuous identity or target binding of a foreign numeric handle. Census snapshots can show `rightsMask` on a handle at a sampling instant, while a handle could close/reuse between samples.
- `correlate` (rights_correlation.py:133-228) requires an accepted ETW direct-open, matching source identity, prior request/right and bounded source lifetime; the optional Census observation is labeled `census_sampled` versus `unverified`. The server additionally checks accepted ETW refs, rights and counts (Server/evidence.py:96-130).
- **Three independent facts:** ETW direct-open = requested access rights (successful open); Census = rights seen held/granted during a snapshot; Security 4663 = an exercised auditable right, where coverage existed. Exercising VM_WRITE does **not**, alone, prove a successful lasting modification of game memory or a rule violation. This remains client-origin evidence subject to manipulation; no new tamper-proof claim is justified.

## 6. Server semantics: currently conservative but conflated

run_diagnostics.py:75-96 defines `queryCompleted` as true only if an audit was armed, the status is collected/partial, no "fatal" issue is present and no local rows were omitted. The "fatal" set includes **`result_limit` and `clock_changed`** as well as real read failures. Thus the field is a **combined coverage/integrity gate**, not a truthful Boolean for whether Windows query iteration exhausted.

Server/sessions/assessment_quality.py:21-26 and 107-138 marks `result_limit`, `clock_changed`, `query_limit`, and `journal_gap` as critical integrity failure, before checking `rowsOmitted` separately. This is deliberately fail-closed and prevents an unjustified green report; however it conflates **loss of displayed/correlatable detail** with **loss of already-counted aggregates** and cannot explain the real capture accurately.

Do not merely delete `result_limit` from the server's critical set without separate completeness semantics and regression tests. A sampled-away foreign event might also be the most important actionable correlation. If read exhaustion is proved but detail is truncated, policy should identify an explicit *detail/attribution limitation*, preserve aggregate counts and any independent findings, and remain inconclusive for claims that require full source attribution. True time/scan/journal failures stay critical. Any wire/assessment v4 change must be coordinated with 07 and feature negotiation/legacy behavior.

## 7. Minimal proposed changes (not implemented)

### Bottom line
