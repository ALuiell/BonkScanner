## 3. Actual cadence, blocking paths, and data freshness

- **Worker main loop:** `worker.py:456-470` retires IPC ACKs, runs `engine.poll()`, serializes/offers events to a bounded credit queue, computes `next_poll_delay()`, then waits. `engine.py:1648-1668` uses the last **actual sample start** and ~100-ms nominal deadline. With pending Census future the loop can wake at ~1–10 ms, but that does not force another fresh read. Windows scheduling and Python waits are **not hard-real-time**. `engine.py:92-95` distinguishes the coarse Windows `time.monotonic` from ETW's QPC/`perf_counter`; compare times on the same domain.
- **Census:** `engine.py:1216-1220` gives **10 seconds** when Direct-Open ETW is healthy. Otherwise fallback is **100 ms only when `sample.active is True` *and* `state=='observing'`**; all other states use **10 seconds**. In `collectors.py:406-427`, `sample.active` signals specific interactables/in-game windows, **not any active combat/gameplay**. Therefore “100-ms active fallback” cannot be interpreted as “100-ms for every playing stage.” `collectors.py:658-751` makes a system handle-table snapshot, starting at 4 MiB and bounded by 128 MiB, with candidate handle duplication and owner identity checks. Snapshots **cannot prove absence between times**. The one-worker executor (`engine.py:111,522-542`) avoids overlapping/catch-up scans; actual check start is distinct from requested time and later application.
- **Existing job durations** (read from first capture `check_requested/actual_start/completed` markers): **260** `held_handle_census` jobs median/max **105.28/213.10 ms**; **28** `environment` **26.05/38.96 ms**; **10** `file_hashes` **92.28/193.73 ms**; **28** `file_metadata` **3.28/5.97 ms**. Median Census start-queue delay ~0.95 ms, maximum 11.48 ms. These durations are **background thread CPU/time**, not main-thread poll block durations.
- **Synchronous pieces remain:** `process_access.py:460-495` polls ETW native stats/drains each worker loop (stats at ~1 s, drains more often), receives images/owner resolution, reports at ~1 s; `engine.py:590-738,1222-1293,1592-1645` consumes completed Census/env/file results, builds payload, runs per-run binding and IPC publication *on the engine thread*. `worker.py:185-292` accounts and serializes each event, replacing some old local diagnostics under pressure. These are credible hot-path candidates but lack timings in the retained trace.
- **Other periodic facts:** environment and file metadata around **60 seconds**, file hashes of the **13 key game files** at run startup / around **900 seconds** (`engine.py:1619-1635`; `collectors.py:852-878,947-1033`). Stable-file hashing requires fstat/stat identity (`collectors.py:120-129`). Results carry run ID + attachment generation, so an old future must be dropped rather than attached to a new run (`engine.py:1229-1251,1592-1602`). Source **freshness is actual sample/check time**, not the later future-result/IPC delivery timestamp. Failures/unresolved are not clean negatives.

## 6. Minimal approved-on-demand diagnostics and future acceptance plan

**No optimization before attribution; no production code change made.** If the user authorizes a future Windows measurement, first add **opt-in, local-only, bounded diagnostic counters**, not a new security sensor:

- `worker.serve` (`worker.py:456-470`): QPC phase duration for ACK retirement, `engine.poll`, `slot.offer` serialization and actual wake time; expected vs actual deadline and process/thread identity.
- `ObservationEngine.poll` (`engine.py:1329-1645`): independently bracket physical `reader.check/sensor.sample`, pre-probe instrumentation, `diagnostic_probe`, `_poll_access`, `ProcessAccessMonitor.poll` `stats/drain/resolve`, Census/env/hash future result application, `_bound_pending`, payload building/flush. Preserve requested/actual/completed/**applied** timestamps and attachment/run IDs.
- `StartupTrace.emit` (`startup_trace.py:34-63`): bounded aggregate timing for scenario-file read, trace lock wait, serialization and append/write. **Never synchronously trace the trace writer recursively**; choose in-memory counters flushed out of the sampling path or an external performance tool. Trace OFF must be genuinely off.
- All diagnostics **must not** increase game-memory reads, change 100ms freshness, rewrite coverage gaps, extend native privileges, introduce an obligatory package dependency, or mis-bind old run events.

**Short CPU phase:** Balanced and warmed matched windows in (a) idle/menu; (b) real active gameplay without `sample.active` prompt; (c) interaction with `sample.active=True`; **Validator OFF/ON** × **trace OFF/ON**. At least two controlled/reordered repeats with identical Scanner tabs/recording/overlay/scan mode, supported game/build, stage/seed, focus, frame cap, render settings and approximate mob density. Use low-overhead Windows per-thread sampling/profiling (e.g. WPR/WPA) to resolve Python/native call stacks, read-only CPU counters by exact PID/creation time, worker QPC poll phase spans and game frametimes; no requirement to rerun the earlier, uncontrolled OFF/ON FPS series. Separate Scanner GUI, scanning thread, worker and extra fixture child.

**20–30-minute soak phase (future only):** Warm up first, observe an uninterrupted supported run and human-approved transitions. ~1 Hz per-PID resource samples: private bytes, working set, commit, process+thread CPU user/kernel time, thread/handle count and identity; per-thread stack/CPU when sampled. Add owned ETW session count and finalizer/metadata/hash executor outstanding work; callback queueDrops, lost ETW buffers/events, Census requested→actual→completed→applied interval and `_census_period` reason, environment/metadata ~60s, file hashes ~900s, owner hash queue, IPC credit/unacked backlog and transport ACK, fresh-vs-cached sampling percentiles and >250/>500/>1000-ms time buckets. Observe Security SACL/policy **only** with independent authorized elevated check. After **Stop** verify worker termination, GUI leaves Stopping, native ETW ownership disappears, Security state restored, bounded finalizer/IPC queues drain or end inconclusive, and Scanner returns toward steady-state resources within 2–5 minutes. Repeat Stop/start cycles if consented.

**Resource interpretation:** Bounded healthy caches (e.g. `engine._timings` deques max256, owner hashes max128, ImageHistory last12, bounded IPC/finalization queues) can remain allocated without a leak. Test a persistent monotone per-cycle slope or unreturned native handles/threads/sessions, not exact equality to pre-warm-up Python RSS. Note temporary Census table allocations up to 128 MiB. Never infer “leak-free” from a single 40-s window.

**Acceptance without hard-real-time promises:** nominal 100-ms deadline with measured distribution, each >500ms gap explained or investigated, and >0.5s run fresh-sample uncertainty represented as a gap; no fabricated continuous coverage between Census snapshots; ETW start/loss/drop/Stop and ImageLoad+**Unload** from a controlled fixture with exact run/target identity and partial on failure; timestamps and correct missing/read_failed treatment for env/files; separate Scanner/worker CPU and resources; no runaway owned resources after Stop; no delivery path upgrading unknown/partial to clean. Report truth and coverage before improving cadence.

## 8. Conclusions and handoff

1. **Confirmed:** All four early >500ms gaps have fast physical reads; three occur before the next diagnostic probe after the read, one after the probe.
