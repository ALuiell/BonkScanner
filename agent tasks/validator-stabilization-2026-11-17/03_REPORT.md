## 2. Ownership chain and invariants actually implemented

1. **Privilege boundary.** An ordinary Scanner launches a separate worker through the standard runas/UAC path; UAC cancellation returns no worker (launcher.py:195–249; worker.py:44–97). The worker authenticates its IPC peer and requires elevation (worker.py:326–379). No Scanner elevation, privileged networking, or stored privileged replay input is needed.
2. **Recovery child identity.** The elevated worker's AuditSession obtains the attached target identity, Security cursor, and a recovery-child instance (security_audit.py:158–183). Recovery starts the same executable under the worker's existing elevation with inherited standard pipes, not another runas or arbitrary script from Scanner (audit_recovery.py:176–197). Its entry point verifies the exact parent PID and creation FILETIME, same executable, elevation, and ancestry through a bounded onefile bootstrap chain (audit_recovery.py:32–41, 150–173; launcher.py:115–161).
3. **Exclusive Validator owner.** The helper holds a Global named mutex with administrator/SYSTEM DACL during snapshot, apply, and restore (audit_settings.py:56–75; audit_recovery.py:113–136). An abandoned mutex can be acquired, but external administrators and other noncooperating software are not serialized by it. Policy is **machine-wide**, not limited to the game.
4. **Pinned target.** AuditSettings opens a process handle with ACCESS_SYSTEM_SECURITY, query and synchronize rights. It verifies PID, exact creation FILETIME, executable basename, and alive state, then retains that OS handle through restoration (audit_settings.py:120–149; launcher.py:71–100). A reused numeric PID cannot silently replace the pinned identity. Keeping a handle can keep an exited process object referenced; whether its SACL remains readable after the specific exit path must be verified on Windows, not assumed from the trace.
5. **Snapshot and temporary changes.** Before making changes the helper queries the single Kernel Object audit subcategory and the process's original SACL (audit_settings.py:151–184). The snapshot retains the masked baseline audit flags, original raw descriptor, intended success bit and intended added success ACE for PROCESS_VM_READ / PROCESS_VM_WRITE; existing failure audit and unrelated ACEs are not deliberately removed (audit_settings.py:14–24, 82–112, 187–196). The operations are sequential, **not an atomic snapshot**. The writer preflights identity, live target, existing SACL, and policy before write, then reads both settings back (audit_settings.py:198–228). SACL descriptor normalization is accepted only when ACE bytes and protection semantics agree.
6. **Owned rollback.** SettingsSnapshot tracks attempted Validator writes and restores a value only if the currently observed value matches its installed representation. Independent changes are preserved and become policy_changed / sacl_changed conflicts, while successful writes are read back (audit_settings.py:230–261). The helper executes rollback in a finally block on a normal command, pipe EOF, or parent-worker exit; two short retries are attempted for failed restoration (audit_recovery.py:85–148).
7. **Completion and IPC.** AuditSession.finish skips the Security query for normal Stop but still closes recovery in its finally block, including after query cancellation and access/query failures (security_audit.py:185–249). The worker and engine drain finalizers on Stop, while the controller preserves unknown status if worker IPC is lost (engine.py:1702–1734; worker.py:139–172, 448–486; controller.py:135–142). The helper may restore after worker death but, by design, cannot deliver a restoration reply to a dead parent. The final result is **not** an independently witnessed post-state.

**Required invariants to retain:** Never reset a setting that the helper did not install; never overwrite a distinguishable external edit; never arm a new recovery owner over a previous active finalization; never change unrelated policy subcategories/failure bits/SACL ACEs; never promote an unavailable or lost restoration result to verified; keep Scanner and delivery unelevated.

## 3. Findings, confidence, and limitations

### F-01 — PROVEN code defect: external-change restoration status is not accepted by the diagnostic contract (P0)

- **Producer:** audit_settings.py:258–261 returns the legitimate status preserved_external_change when an independent edit is detected, even when the other Validator-owned setting was successfully restored. audit_recovery.py:124–145 forwards it; security_audit.py:209–216 includes it; run_diagnostics.py:75–96 passes it into the run-end Security diagnostic unchanged.
- **Validator contract:** protocol.py:1014–1023 permits only verified, failed, unknown, pending, and not_needed. protocol.py:1135–1180 therefore rejects preserved_external_change during DiagnosticSummaries validation.
- **Actual transport consequence:** transport.py:235–253 catches the validation error, silently omits the entire optional diagnostic summaries block, records diagnostics_dropped, and continues baseline final delivery. tests/test_validator_transport.py:552–567 and 904–918 confirm that invalid optional diagnostics are intentionally dropped. This can lose the Security status, not just individual rows.
- **Server contract:** contract/v3/schema.json:2832–2839 independently omits the same status. Server assessment_quality.py:107–124 treats an explicitly nonverified restoration as a critical audit_restoration_unverified, whereas entirely missing Security evidence is classified audit_unavailable / limited. Omission can therefore distort assessment as well as diagnostics.
- **What is proved:** the cross-layer enum mismatch and its deterministic validation/drop path, by static tracing. **Not tested here:** a real external-policy-edit execution and a complete server response exercising that branch.
- **Minimal fix for integrator:** choose a stable, end-to-end representation for preserved_external_change (prefer explicit separate status with field-level issues, rather than disguising it as verified); update Validator protocol.py, server contract/v3/schema.json, the corresponding wire conversion/validation, server assessment_quality.py and tests together. Maintain critical/unknown handling until restoration is independently justified. Add an offline transport regression showing the whole diagnostic is retained and no favorable classification is inferred. New sensor/dependency: **none**.

### F-02 — Existing restoration guard is substantial, but a normalized-SACL edge needs a targeted test (hypothesis)

audit_settings.py:204–212 first stores an observed, OS-normalized installed_sacl and **then** rejects a changed SACL-protection bit. A synthetic interleaving in which the protection bit was changed by an external writer at that instant may be incorrectly viewed as the helper's installed representation during finally/restore. That could conflict with the preserve-external invariant. This is a **static hypothesis**, not an observed Windows defect; descriptor behavior and reachable race timing remain unknown. Gate any modification on a controlled fake-settings interleaving plus an owned-process Windows reproduction. A conservative candidate is to validate all normalization invariants **before** committing installed_sacl to the owned-write snapshot, while retaining successful Windows descriptor round trips.

### F-03 — Worker death is supervised; helper death is not recoverable by that helper (architectural limit)

audit_recovery.py:93–105 watches parent exit and pipe EOF; 113–136 restores in finally while holding the pinned target and mutex. worker.py:342–352 may forcibly terminate a stuck worker during shutdown; helper survival and cleanup are distinct. If only the worker dies but the helper stays alive, helper rollback is designed to continue, but there is no reply to the dead worker; independent verification is necessary. If the **recovery helper itself** is forcibly terminated after installing changes, no live owner retains its in-memory snapshot; the mutex does not restore machine policy or a SACL automatically. Consequently, do not claim crash-proof restoration or auto-reset global policy from stale local state. A safe future mitigation, if a real defect warrants it, must preserve externally made settings and must receive a separate design/scope decision.

### F-04 — Missing independent restoration evidence in the latest real run is NOT proof of a stuck policy

- Current 09:30 real-stage trace: sequence 15 reports setup status armed and explicitly actual_activation=unknown, reason=recovery_acknowledgement_only. Sequences 20616/20623/20669/20679–20683 show run-end finalization and a Security result partial, with late_attachment, clock_changed, run_boundary_unknown, result_limit, 0 confirmed and 24 retained ambiguous rows. The audit_final_result_observed trace event logs no restoration status, policy flags, or SACL bytes (engine.py:903–918). Sequences 30730–30733 show a later Stop when setup_present was false.
- Heavy-wave trace: sequence 15 also reports arming acknowledgement only; sequences 9620 and 9623–9627 show Stop, cancelled Security result with late_attachment, and finalizer completion. They do not show independent post-state.
- Direct GameLab C05: sequences 13575 and 13669 show audit_arm_deferred during old finalization; 13651 and 13743 show prior audit results before new arming (13656 and 13748). This supports serialized *reported* finalization, not independent Windows rollback.
- The historical independent auditpol test on 2026-11-17 failed for lack of privilege (Windows 0x522) as recorded in FINAL_REAL_STAGE_REVIEW_2026-11-17.md:35–41 and QA_HEAVY_FINAL_2026-11-17.md:49–51. That result is **unknown**, not pass, not failed rollback.
- Previous owned-target and controlled live-game experiments on Windows build 26200 did record independently verified post-state: docs/validator/experiments/security_4663_e2_2026-11-12.md:20–24, 34–45, 59–61. Those separate probes were not the current full source/packaged Scanner run and cannot certify its exit, overlap, or crash behavior.

**Unavailable from the latest saved captures:** an independent elevated before/during/after policy read; original and installed raw SACL/protection/ACE snapshots tied to the target's exact FILETIME; an independent post-Stop target-handle read; a supervisor-independent watcher for helper PID/exit; a controlled forced-worker/helper-exit restoration test; reliable postmortem proof after the target's kernel object has disappeared. No new Security 4663 query/replay was run for this report.

### F-05 — Windows concurrency and target-exit boundaries

Windows AuditSetSystemPolicy and process SACL setters are not transactional compare-and-set operations against all outside processes. The named mutex protects cooperating Validator instances only; a malicious or ordinary privileged outsider may write between read and set, or may write the same representation (undetectable). This limitation is documented in functional_updates.md:137–147. A pinned process handle is needed **before** the target exits if a later SACL read is to be attempted. Once the process object is destroyed and no suitable security handle exists, a new inspector cannot reconstruct its former SACL. The global subcategory remains independently queryable after game exit. Never label missing exited-object SACL as verified merely because global policy looks restored.

## 5. Independent elevated diagnostic protocol — proposed, NOT TESTED

Use an **isolated owned Windows test target**, not the current user's live MegaBonk run. The checker must be a **separately launched, normally UAC-elevated inspection process** with only needed privileges; it must not inherit trust from Scanner or rely on the helper's own reply. No UAC bypass, no injection or gameplay modification, no privileged Scanner/network process. Record checker executable/revision, target OS build, boot identity, exact PID and creation FILETIME, UAC state and SeSecurityPrivilege availability, local UTC timestamps, worker/helper PIDs, and each operation's result/error. Avoid publishing raw ACLs, processes or security events to the public server.

**A. Before arming:** Identify and keep open a suitable target process handle while it is alive. Verify its PID, creation FILETIME, executable, and access to SACL_SECURITY_INFORMATION. Read the Kernel Object audit subcategory by its GUID with AuditQuerySystemPolicy, and SACL with GetKernelObjectSecurity. Record raw descriptor bytes and parsed ACE list, SACL control bits (especially protected/auto-inherited), relevant policy success/failure bits, and errors. Also record if policy was already enabled by another administrator: the test must not assume the global baseline is No Auditing.

**B. During arming:** Start the worker only through the supported opt-in/UAC interface, if this is a permitted future controlled test. After a helper armed acknowledgement, independently re-read the same global policy and pinned target SACL; demonstrate the newly enabled success bit and the audit ACE or correctly document a pre-existing identical value/no-op. Keep the target handle alive for the whole trial. Do not confuse helper acknowledgement or a Security log record with the independently observed state.

**C. After cleanup:** For each branch, re-read *each* policy/SACL independently while its object is available, including after the helper and worker exit. Record compare-to-baseline and compare-to-installed results, SACL semantic equivalence and raw byte equality separately, all original unrelated audit/SACL entries, failure-audit bit, and Win32 errors. If the target has exited, the machine policy can still be queried; SACL verification is possible only if a suitable handle still references the object and Windows permits the query. Otherwise label SACL unknown, not verified. Keep raw evidence local and bound to the observed revision and scenario.

**D. External-change injection:** Only on the owned stand, optionally have a distinct elevated actor make a known, recorded edit to a policy or SACL field. Never use a live third-party change as permission to reset global policy. The checker is read-only during normal diagnosis. After an intentional checker-owned change, undo **only the checker's own contribution** if current state is still exactly the checker-installed representation; otherwise preserve the unexpected external change and stop for manual review. Do not blindly apply the initial baseline after a conflict or after an unrelated admin policy change.

**Outcome rules, evaluated per policy and SACL (then combined):**

- **verified:** independent post-read of every accessible relevant field equals the pre-arm baseline (or a documented semantic-equivalent SACL normalization with unchanged ACE/protection semantics); exact object identity is still pinned; all Validator-owned changes have been removed or were no-ops. A helper response alone never suffices.
- **preserved_external_change:** a controlled, distinguishable external edit remains intact; any independently verifiable Validator-owned companion field is restored; no third-party value was reset. Treat as safe conflict handling but **not** a clean restoration/green audit.
- **failed:** while a valid independent read is possible, a Validator-owned temporary policy bit/ACE persists beyond expected completion, restore readback fails, or a foreign change is overwritten. Report affected component and error; do not perform a blind global repair.
- **unknown:** permission 0x522/access denial, baseline not captured, target security object no longer available, missing helper/worker/after-state, ambiguous race, or insufficient identity evidence. An unknown SACL plus verified global policy yields overall **unknown**, not verified.

Machine-wide audit policy must be checked *both* during and after. Policy restoration is not the same thing as SACL restoration, and successful 4663 collection is not proof that either was reset.
