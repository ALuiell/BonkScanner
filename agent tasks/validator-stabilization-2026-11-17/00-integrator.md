## Как провести работу

1. **Сверка и baseline.** Для каждой заявленной проблемы найди актуальный код и конкретное доказательство. Сопоставь связи 05 → 01 → 02 → 07 для границ и качества, 03 ↔ 04 для восстановления/владения, 04/06 → 07 для доставки, gaps и ресурсов. Исследовательские отчёты сами по себе не доказывают новую приёмку. Начни с минимальных offline регрессий и недостающей диагностики для P0. Если выводы расходятся, выбери проверку, которая их различает.
2. **Реализация.** Исправляй подтверждённые дефекты малыми изменениями и проверяй их совместно. У Validator — собственный engine, clocks, IPC, worker, collector, transport. У Scanner — GUI, shutdown, recording и report links. У Server — контракт, ACK/persistence, версии, классификация и проекции. У GameLab — только подтверждённая проблема тестового управления, если это понадобится. Проведи через одного исполнителя все пересечения в `engine.py`, `controller.py`, `worker.py`, `transport.py` и wire/contract. Если правки пользователя пересекаются с исправлением, работай в отдельном рабочем дереве с явным baseline. Не переключай ветку в общем Scanner checkout без проверки вложенного Docs по AGENTS.md. Не делай бросовых worktrees без нужды, reset/clean, commit/push или деплой без отдельного запроса.
3. **Сначала локальный offline/сервер.** Запусти существующие suites и новые точечные регрессии для исправлений. Повтори применимые P07/P08/saved replays, Validator, Scanner UI/recording/report, при необходимости GameLab offline, контракт и PostgreSQL/Django с retry после lost ACK, перезапуском и browser/public/private. Используй локальный dev Compose по README Server либо существующее разрешённое окружение, не печатай секреты и не используй production. Зафиксируй какие прогоны synthetic/source, какие проверяют реальный ACK и сохранение.
4. **Один Windows-стенд, один последовательный прогон.** Перед live проверь затронутые процессы, ревизии, сборку игры и baseline настроек. Scanner должен остаться обычным пользовательским процессом, worker запускается через штатный UAC. Проведи сначала smoke игры/GUI и независимую проверку recovery. Затем совмещай C05/Stop, ETW/census/image, Security и доставку там, где один сценарий проверяет несколько критериев. Длинный прогон проведи после стабилизации коротких. Для GUI используй window-specific UI Automation/Win32 и заново проверяй HWND/PID. Никакого глобального мышиного/клавиатурного ввода или захвата фокуса. Для GameLab сначала прочитай `F:/Python/BonkScanner_experiments/AGENTS.md`, `F:/Python/BonkScanner_experiments/manifests/tools.json` и `F:/Python/BonkScanner/docs/development/game_lab.md`, проверь build и результат JSON/receipt каждого действия. `failed_or_unknown` не повторяй вслепую. Используй штатные права, не обходи secure desktop. Изменение системного времени проверяй через часы фикстуры и, если нужно реальное изменение, на отдельном разрешённом стенде. Если native проверка недоступна, продолжи остальные и опиши конкретный блокер.
5. **Подтверждение результата.** Для каждого сценария запиши ревизии, среду, команду или шаги, ссылку на фактический evidence и ожидаемый инвариант. Сохраняй только диагностически нужные новые данные в отдельной папке для этой приёмки, существующие captures не меняй. При ресурсных проверках проверяй хвост очередей, ETW, потоки и ownership после Stop. После Windows-проверок независимо проверь возврат audit policy/SACL в исходное состояние там, где объект жив, и зафиксируй судьбу процесса для веток выхода. Чужие изменения политики не откатывай без подтверждённого ownership.
