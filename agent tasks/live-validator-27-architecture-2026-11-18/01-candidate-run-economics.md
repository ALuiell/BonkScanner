## Что установить по имеющимся данным

1. Построй три непересекающиеся категории: native попытка до подтверждения (<1 активной секунды), подтверждённый локальный Validator run с коротким наблюдением (<15 секунд до publish gate) и ран ≥15 секунд. Раздели `run_start`, фактический HTTP `POST create`, строку PostgreSQL, доступность публичного отчёта и подтверждённый finish. Для паузы используй игровое активное время только там, где код его действительно использует; длительность payload и серверного `observed_duration` считай по их правилам.
2. Проследи фактическую последовательность `create → batch/heartbeat → finish → ACK → close/timeout → sweep/delete`. Назови записи PostgreSQL по типу: upsert EnrollmentWindow, insert Session, последующие update Session, очистка непубличного evidence, удаление. Не объявляй число логических ORM операций фактическим disk IO/WAL без сохранённых метрик. Отдельно оцени 0–10-секундный enrollment jitter, 10-секундный batch, 15-секундный publish, 30-секундный stale, 900-секундный inactivity и 900-секундный provisional ACK retention; не складывай их в один «TTL».
3. Используй только существующие трассы в `F:/Python/BonkScanner/.local/validator-start-trace/` и `agent tasks/validator-stabilization-2026-11-17/acceptance/`, если они содержат подходящие события. Сопоставляй `localRunId`, session ID, HTTP receipt/ACK и DB receipt только когда эти значения реально сохранены. Если HTTP или DB событий нет, рассчитай нижнюю/верхнюю **source-model** оценку потенциальных запросов и строк с явными допущениями; не выдавай её за измерение VPS или цену в USD. Укажи минимальные будущие поля/счётчики для замера, без реализации и запуска.
4. Проверь safety гипотетической задержки: конечный максимум latency, сохранение всего уже принятого неблагоприятного evidence и unknown gaps независимо от текущего `assessment.status`, immutable in-flight payload/ACK, отдельные `localRunId` при быстрых соседних ранах, выход/краш/отсутствие сети до enrollment, лимит 15 MiB и поведение при переполнении. Непосланная попытка не может становиться `clean`. Нельзя «оптимизировать» короткий ран лишь по SEARCHING/FOUND/menuMusic.
5. Сравни no-change, более точную диагностику и отложенный enrollment по независимой пользе, CPU/RAM/HTTP/DB нагрузке, риску потери findings, сложности миграции протокола и восстановлению после перезапуска. Сохрани v3 API negotiation, pinned registry/catalogue и исторические отчёты; D2/v5 и detector принадлежат другим решениям. Не предлагай серверную классификацию клиентских flags как античит.
