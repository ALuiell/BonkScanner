# Security 4663 collection over a ten-hour run

Research decision, 18 November 2026. **NO-GO for implementation.** The saved native evidence proves loss of event **details** through the 24-row group cap while the read/write record aggregates survive. In the strongest packaged example, the final read exhausted 316 eligible records in approximately 0.372 seconds and omitted 292 details. That segment ended with `context_lost`. Loss caused by either query budget or by Security log overwrite on a ten-hour run is **NOT OBSERVED**. Use the existing end-only reader as the future measurement baseline. There is insufficient evidence to raise its budget or replace it with a periodic reader.

## A/B/C comparison

The threat addressed is missing or misleading 4663 evidence during long observation. ETW direct-open and census cover requested or held rights, modules/mod/loaders cover loaded software, and file checks cover key on-disk files. None measures lost exercised-right records. A reader changes reliability within one evidence channel. It adds no independent detection or prevention and cannot attest a user-controlled report. No new driver, service, game modification, privileges or wire part is warranted by the saved evidence.

`H` is an explicitly bounded active duration, `P` a future minimum interval between scheduled reads, `N` a hard per-run attempt cap including final and retries, `K` a per-attempt returned-record cap, and `Q` a cooperative per-attempt query deadline. For ten hours `H=36,000 s`. If a future implementation admits at most one scheduled query per interval and separately caps retries plus tail attempts at `J`, the attempt count is at most `min(N, ceil(H/P)+J)`. `N×K` and `N×Q` are workload and nominal elapsed-budget envelopes, not Windows throughput, IO bytes, CPU time or a hard native wall bound. If the run or retry cap is exceeded, record unfinished coverage as partial. A real bound must include native call contention, handle cleanup and restoration, with cancellation and owner recovery verified under a stall. No fixed polling period, including five minutes, is supported by these observations.

## Conditions for any incremental design

1. **Arming and continuity.** Keep the exact target process instance, `localRunId`, attachment generation, session/recovery ownership and Windows channel identity together. Establish the first safe audit boundary from verified setup and bound run state. Keep earlier time explicitly partial. Arming reads a journal baseline before helper launch and records `armed_at` on the helper ACK (`security_audit.py:277–299`). Query start is `max(start, armed_at)` and the ACK does not measure the start of native auditing. For each proposed range capture coherent generation and oldest/high state before and after. A creation timestamp is a generation signal subject to clear/recreate validation, with ambiguity treated as a gap. Keep full/clear and interruption checks. An unchanged sampled tuple cannot prove the absence of an unseen clear or policy excursion.
2. **B time-window rules.** Use bounded overlap and epoch-scoped `(epoch, EventRecordID)` dedup across every window that could still encounter a repeat. A time frontier advances only after the complete overlapping query is validated and after justified retention and delivery checks for the sealed time interval. Account for timer jitter, standby, a skipped poll and retention movement while reading. A late event may have a new ID and an event time earlier than the overlap. A finite UTC overlap by itself cannot rule that out. Require either independent evidence of a safe lateness and retention envelope with a way to detect violations or a record-range continuity check that effectively adds a checkpoint. Dedup overflow, unresolved overlap or unsupported clock behavior makes the affected range incomplete. Keep only the evidence that can still be assigned without double counting.
3. **C record-range rules.** Let `W` be the last fully accepted channel high boundary and `U` a safely sampled high boundary for the next query. In the same generation, query scoped events in `(W,U]`, with local run-time classification. Validate that the range is contiguous in coverage even when matching rows have nonconsecutive IDs. Empty EOF can advance through a verified retained channel range. The last matching row is insufficient to establish the channel frontier. If oldest is `W+1`, the next range can still be intact. Oldest beyond `W+1` before or during the proof means an unverified unread prefix unless independent evidence proves it was already covered. Regressed high, reset/reused IDs, unexpected epoch, full state, torn range, render/parse loss and unknown oldest all fail closed. Explicitly include 1102 and other interruptions and Kernel Object 4719 without relying solely on the current run's UTC predicate for continuity. Test sentinel handling for an initially empty channel and the actual Windows query/view consistency under concurrent appends and wrap.
4. **Atomic merge and accounting.** Stage a batch under its expected predecessor and epoch. Only a complete validated batch can commit its counters, details, issues and advancing frontier as one transition. An identical repeated range commits once. A transient read error can be recovered by rereading the same entire demonstrably retained interval before freeze. Until then, and after any permanent hole, represent the unresolved interval as partial or unavailable. Preserve prior committed counts and retained adverse evidence. If keeping observed rows from an incomplete attempt for triage, keep them provisional and bounded, then replace/reconcile on retry before adding them to authoritative aggregates. Discarding a range of unknown cardinality must never introduce zero observations or a full status. A later successful batch cannot make an irrecoverable earlier gap clean.
5. **Clock and delayed tail.** Use stable UTC/QPC brackets and bound samples to assign event time. `engine.py:49–79,899–957,981–1012` guards the run, freeze and pre/post query. Record order can establish delivery progress even when event time regresses, provided generation/order are verified. It cannot establish trustworthy run membership through a step, slew or missing bracket. Retain counts in an appropriate ambiguous/partial state under existing semantics and keep omitted counts when demoting. A long-running reader must prevent early irreversible “confirmed” or correlation claims if a later clock guard invalidates the mapping. Keep correlation bounded to the existing justified evidence and sampled detail. For delayed delivery, distinguish a channel frontier from an event-time frontier: a newly appended ID with old UTC still needs consideration for the original run. Avoid discarding recent out-of-time candidates on the assumption they are duplicates. Verify the chosen drain with independent delayed ground truth during acceptance. With a frozen unknown game boundary, a successful drain cannot extend coverage through an unobserved end.

## Recovery, final tail and wire ownership

`audit_settings.py:35–75,120–149,183–261` gates the helper under `SeSecurityPrivilege` and a protected mutex, verifies target PID + creation identity through a pinned handle, and snapshots the process SACL and the Kernel Object success policy. The helper applies only the required changes and verifies readback. It restores each value only when it still owns the installed representation, preserves external modifications, and verifies restoration by rereading. A returned full journal read and a reported `verified` restore are independent. A policy or SACL change and reversion between samples can evade the endpoint comparison. The protected mutex coordinates cooperating helpers. It does not serialize outside policy writers.

`audit_recovery.py:91–153,244–267` holds recovery until the pipe command/EOF or actual worker death. The helper retains the original snapshot and target, makes bounded retries for transient restore failures, and owns cleanup even if the worker no longer receives a reply. The worker close receipt wait is 0.6 s and may wait again if a late `armed` reply arrives. A lost receipt yields `unknown` and `restoration_failed`. Worker death is designed to trigger helper cleanup. Simultaneous helper and worker loss, unavailable target readback or a hung native call cannot establish restoration. Keep diagnostics and incomplete status on those paths. B/C must never reinstall settings per batch, acquire a second helper for the same audit, let a checkpoint restore any settings, or carry a cursor across worker death as if it proved the new owner's coverage.
