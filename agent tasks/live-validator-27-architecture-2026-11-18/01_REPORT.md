## Run cohorts and evidence

Use three disjoint cohorts. **A** is a native attempt superseded before the observer credits one second of fresh, active timer progress. Unobserved native attempts and unresolved transitions have uncertain duration. **B** is one confirmed local Validator run with less than 15,000 ms of server-accounted observation. It can still publish on a finding. **C** is one confirmed local run reaching at least 15,000 ms of server-accounted observation. Where no server payload/watermark exists, a short or long local time proxy is reported with the server cohort unverified. Keep unclassifiable samples explicit.

The units differ. The detector accumulates fresh, compatible advances of the game timer, credits at most eligible entry-to-pause movement and gives frozen paused polls zero credit. The worker assigns a UUID at confirmation, then computes payload offsets from its observer clock origin. Capture offsets can advance during an observed pause. The v3 server uses the accepted `capturedThroughMs` minus the union of all-channel gaps clipped to the watermark, including open gaps through the watermark. Individual sensor gaps and a zero-length process-access marker do not subtract time from this gate. Freshness uses the server's clock and last accepted progress. A heartbeat can refresh freshness while leaving the observation watermark unchanged.

A worker `run_start` supplies a `localRunId`. The controller can fail to allocate transport capacity. An HTTP create attempt may fail before acceptance or succeed without its response reaching the client. A committed Session gets a server UUID. A public report needs server availability, and the Scanner v3 link waits for availability in a valid ACK. A finish request, server-committed finish, client receipt of a matching finish ACK, and confirmed game end are four separate facts. Server state is `completed` only with accepted `confirmedRunEndMs`; a finish with an unconfirmed boundary can close as `interrupted`. Evidence and verdict can remain partial even on a completed report.

## Request and row model

1. **Create.** Client `transport.py:126-132,179-200,217-253,439-469,481-503` schedules initial enrollment uniformly between 0 and 10 s after local allocation. Local finish sets `next_at=0`; the sender still chooses create if it lacks a server UUID. Jitter spreads sends when the endpoint and send slots are available. Busy slots, retries, missing endpoint and shutdown can change actual timing. Server `sessions/views.py:45-53`, `sessions/enrollment.py:23-77` validates the request, performs one logical PostgreSQL `EnrollmentWindow` upsert for the direct peer's keyed address when the limiter is enabled, and inserts a new provisional `Session` with pinned rules and token digest in one transaction. Server `validator_server/settings.py:36` defaults to 60/min per peer. This is a single counter row per peer, updated across windows. A rejected 429 can exercise the upsert predicate without incrementing the window or creating a Session.
2. **Batch, heartbeat and finish.** Create ACK makes the next request immediately eligible. A normal successful batch schedules the next idle tick after 10 s. Queued fragments, terminal work or loss can schedule immediate sends. Local payloads can be emitted on a roughly 1 s cadence and v3 framing may split them. Empty heartbeat uses the acknowledged watermark. The v3 sender can carry the last fragment in finish, avoiding a separate mutation for that fragment. See Client `engine.py:1775-1785`, `transport.py:335-434,454-468,493-535`. Server delivery authenticates, hashes operation and canonical body, locks the Session row and commits one logical Session update per newly accepted mutation, including sequence, watermark, compact evidence, freshness and ACK. Another HTTP call for an exact last-sequence replay returns the stored ACK, with no second payload application or freshness advance. A replay or rejected mutation can still trigger due lifecycle maintenance. Invalid or conflicting requests have request processing and may take a row lock even when they consume no sequence. See Server `sessions/delivery.py:37-142`.
3. **Publication and close.** `should_publish` evaluates accepted observation or a pinned server finding, with sticky availability after first publication. Under current v4, a classified loader/environment or file-integrity finding can publish below 15 s. Access capabilities and private denial/correlation context alone have different semantics. Finish closes inside its mutation update. A provisional closure clears evidence, binding and accepted features and retains the last ACK and digest. A public closure retains compact evidence. The v3 link uses the ACK, independently of local Scanner history filtering. See Server `sessions/delivery.py:61-115`, `sessions/classification.py:473-555`, `sessions/lifecycle.py:18-26,46-65`, Scanner `src/app/validator_reports.py:25-63,176-216` and `src/ui/validator.py:514-545`.
4. **Stale, timeout and sweep.** At 30 s without accepted progress, freshness becomes stale and the sweeper can write a network gap. An accepted new mutation can resolve it. At 900 s of inactivity, the effective timeout closes a session. The closed, nonpublic row retains its last replayable ACK for another 900 s from the effective close. A public report has a separate 90-day retention deadline after close. The sweep deletes expired rows and independently removes enrollment counters whose window timestamps are more than two minutes old. Local Compose schedules a 30 s sweep with a default batch limit of 500 timed Session rows per call. Due rows can be handled later because of scheduling, backlog or row locks. Public visibility also checks deadlines on read. See Server `sessions/contract.py:9-18`, `sessions/lifecycle.py:11-26,29-43,54-105`, `sessions/reports.py:22-35`, `compose.yaml:35-39`. A late sweep can delete a row directly if both deadlines passed.

## Evidence safety and options

- **Deadline.** A wait for 15 seconds of active play, a Scanner status transition or the latest verdict can persist indefinitely during a pause, menu ambiguity or outage. Any later prototype must establish a fixed monotonic deadline for its intentional delay measured from local confirmation, unaffected by pauses, hints, verdicts or later attempts. Terminal and adverse evidence and approaching capacity need a prompt delivery path. Prove the added delay ceiling under a healthy sender and state explicit unconfirmed outcomes on outage or process death. Actual remote acceptance has no finite guarantee when the server or network is unreachable. A safe numeric delay and an acceptable bound for time-to-first durable evidence are **NOT OBSERVED**.
- **Retention and identity.** Preserve every accepted adverse fact and unknown interval even if current assessment is `inconclusive` or an observation changes category. Keep accepted server evidence and original ACKs attached to their original session. Preserve queued file/loader observations, process-access context, gap endpoints, clock origin and terminal facts from the original run through its own finalizer. Existing code and C05 show old terminal delivery after a new start. Keep separate `localRunId` values and original sequence ownership. Preserve immutable in-flight bytes on transport retry and release capacity only on the matching valid ACK. The existing optional-correlation validation fallback occurs after a 400 for an unconsumed sequence. Preserve the distinction between this fallback and a retry of accepted bytes. See Client `controller.py:192-255`, `transport.py:513-557` and Server `sessions/delivery.py:45-58,89-115`.
- **Shutdown and capacity.** Client `protocol.py:958-962` and `transport.py:58-75,177-200,335-365,672-693` set a shared 15 MiB queue accounting budget with a 4 KiB reserve charged per local session and a 32-session limit. The advertised 16 MiB policy value is separate. Neither figure measures full process RAM. Payload and framing overflow write explicit queue-loss gaps, can drop unsent observations and can remove confirmed end credit. The reserve covers loss reporting. The controller normally calls close with a 3 s drain budget. The transport's standalone default is 5 s. Close marks unconfirmed finishes and records whether queued bytes were discarded. Abrupt process death loses RAM payloads and tokens, even if server rows already exist. Delaying create extends this exposure and can move short-run evidence into contention with neighboring runs. Crash-durable recovery would be a separate storage, privacy and lifecycle decision. Current server-side saved ACK durability cannot recover a restarted client's lost token and request bytes.
- **Hints and trust.** Scanner search intent belongs to `src/gui_scanner.py` (`Scanner._resume_scan` :554-568, `_run_background_loop` :1106,1198-1238,1265-1281). The search loop evaluates templates and, on a confirmed target window, sets `pause_reason="target_found"` and clears `scan_event`. `update_status_ui` at :381-440 renders local states including RUNNING and ARMED. SEARCHING/FOUND are useful descriptions of that workflow. `src/app/validator.py:4-14` constructs the independent controller, and `src/ui/validator.py:235-243,279-319` selects v3 and displays Validator state from its snapshot. For an already bound run, Client `engine.py:498-526,1641-1661` uses menu music as one input with frozen timer, fresh samples and continuity. Neither client-controlled hint establishes evidence safety, server identity or consent to skip enrollment. An unsubmitted or unobserved interval remains unknown. Documented detection stays with external process access, loaded module/loader evidence and key file integrity. Access rights express capability. The catalogue interprets already accepted observations and client data carries no remote attestation.
